# 2026-10-30 mcp: a busy status poll no longer ends a capture sequence (#179)

Focus: mcp · Commits: 0a370d6 · Machine: bmb (Mac, worker bevy_emerge_w2) · Outcome: fixes only

## Summary
`emerge_capture_sequence` refused the whole sequence when one `emerge/capture_sequence_status` poll outran the 5 s read budget, which killed three clip recordings on bmb. A busy poll now counts as still running and only the sequence deadline ends the wait.

## Baseline
Gate: pre-push gate on push. `accept.py`: not run (time budget; the change is confined to the MCP server's capture poll, which no accept step drives). Load 14.9–16.1 on 14 cores, free disk 26 GB, 48 GB RAM.

## Bugs fixed
### #179: emerge_capture_sequence gives up on one slow status poll
Must-fix: blocks y (clips cannot be recorded on the Mac worker under load), common y (3/3 attempts at load 17), no workaround y.
Root cause: the poll loop in `main.rs` returned `refusal(&e)` on any `Brp::call` error, and a per-call timeout is one.
Fix: `Brp::call_unless_busy` (`brp.rs`) answers `Ok(None)` for a timed-out call; `sequence::wait_for_sequence` (`src/sequence.rs`) counts it and polls again until the deadline; a missing editor or a refusal still ends it.
Regression check: `crates/bevy_emerge_mcp/tests/a_slow_status_poll.rs::a_poll_that_runs_out_of_its_budget_is_still_running` failed before with "the editor did not finish `emerge/capture_sequence_status` within 5 s, so the call was abandoned", passes after; `polls_that_never_answer_end_at_the_deadline` pins the deadline (failed before: the refusal did not name the unanswered polls).
