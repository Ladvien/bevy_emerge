# 2026-10-26 view: a map whose stacking does not resolve still opens framed (B-018)

Focus: view · Commits: `f2b3461..23d2c41` · Machine: big (`Cs-MacBook-Pro.local`, no Sanctuary checkout) · Outcome: fixes only

## Summary

`resolve_frame` resolved every placement's Y before it read the target, so `FrameTarget::Map` — which
reads only `map_bounds`, the floor plan and the height span — was refused by a bad stack. The author
got a toast and an 18 m close-up at the origin instead of the map. The stack is now resolved by the
three targets that stand pieces on something (`Selection`, `Placements`, `Rect`) and not before;
`Map` frames the map's own box, and the stacking reason is asked for separately and still reported, so
the frame was not bought by silencing the authoring error.

The planned enhancement was **not shipped**, and the reason is structural rather than a lack of time —
see "Blocked: a new operation cannot pass the parity ratchet from a loop pass".

## Bugs fixed

### B-018: a map whose stacking does not resolve opens unframed on the 18 m close-up

Must-fix: blocks **n**, common **n**, no workaround **n** — 1 of 3, taken anyway because the fix is four
lines and the defect is a frame that shows the author the wrong thing on the first frame they see.

Root cause: `editor.rs::resolve_frame` opened with `let ys = heights(project, open)?;` — an eager
stack resolution that only the `Selection`, `Placements` and `Rect` arms consume. `FrameTarget::Map`
returns `map_bounds(open)`, which is `floor_rect` + `height_span` + `bounds` and touches no
placement. So one unresolvable stack turned "frame the whole map" into `Err`, and
`frame_map_on_open` put that in `status.problem` and left `Rig::default()`'s 18 m view.

The reachable broken stack is **not** a missing host: `Map::validate` already refuses
`rests on 'x', which does not exist`. It is a host that exists and offers nothing the guest needs —
measured here as a `worktop`-mounted lamp seated on an `OnFloor` floor tile, which `resolve_y`
refuses with *"`lamp@2` needs a `worktop` surface and rests on `floor@0` …"*.

Regression check: `tests/a_broken_stack_still_opens_framed.rs`
- `a_map_with_a_broken_stack_opens_framed_on_the_whole_map` — **failed before** with *"a corner of the
  1120 m map is outside the camera's view — a map whose stacking does not resolve still opens on an
  18 m close-up of the origin"*; passes after.
- `a_map_with_a_broken_stack_still_reports_the_stack` — **failed after the first version of the fix**
  (the status held ``), which is what forced the report to be kept. It caught the cheap fix.

### Blocked: a new operation cannot pass the parity ratchet from a loop pass

E-066 (`map_remove`) is the obvious next step and the chooser's `Delete` row is a genuine parity gap —
`confirm_delete_entry` calls `std::fs::remove_file` / `remove_dir_all` directly, outside the registry,
which the brief names a must-fix class. It cannot land this pass:

`tests/operations_have_two_front_ends.rs::every_operation_has_a_ui_entry_point_and_the_other_way_round`
enumerates `ops::registry()` and fails any operation missing from `UI_ENTRY_POINTS` /
`CHOOSER_ENTRY_POINTS`. **Those two tables are `const`s inside the test file**, which
`.omp/commands/build-loop.md` makes read-only. A new operation therefore cannot be added without
editing a protected file — so the pass stops rather than reasoning its way to an exception.

The fix is a human/evaluator-pass decision, and it is small: move the two tables out of the test into a
product constant (`ops::ui_entry_points()`), so a new operation and its entry point are one commit in
product code and the ratchet still bites. Logged as E-086 with that proposal.

   operation needed, so it is *not* blocked. Chosen as next focus.
2. **E-066** `map_remove` — blocked as above.
3. **E-060** `mount_options` offers the two-way mount for one surface class only — product-only, small.

## Review

Reviewer **could not run** (cloud rate limit). Self-review, mine:

1. **Does the change do what the commit says?** Yes — `heights` is now called inside the three
   placement-reading arms; `Map` reads only `map_bounds`. The failing-before test is the evidence.
2. **What could it break that no test covers?** `emerge/frame_view {target: rect}` now resolves heights
   one statement later than before, inside the arm, after the rectangle's own validation. So a bad
   rectangle with a bad stack now reports the rectangle, where before it reported the stack. That is
   the better order (the request's own fault first) and no test asserted either.
3. **Is the report duplicative?** `frame_map_on_open` now calls `heights` a second time after
   `resolve_frame` has already skipped it. Two walks over the placements, once per door crossing. It is
   O(n) and it is where the sentence comes from; the alternative is a second return channel from
   `resolve_frame`, which is a bigger change for a one-shot system.
4. **Is the second test tautological?** No — it failed on a real intermediate version of this diff, and
   its failure message named the empty status. That is the strongest evidence available that it bites.
5. **Does the fix weaken a check?** No test file was edited. One new test file added.
