# 2026-10-27 kits: every surface class gets its own `or floor` mount (E-060)

Focus: kits · Commits: `0ffbd13..f0b2145` · Machine: big (`Cs-MacBook-Pro.local`, no Sanctuary
checkout) · Outcome: shipped

## Summary

`Mount::OnSurfaceOrFloor` says a piece may rest on a support top **or** on the floor, and
`mount_options` offered it for `surfaces.first()` alone. `assets/emerge/vocab.ron` declares three
classes — `support`, `worktop`, `shelf` — so an author cycling `M`, or the labeller choosing a mount
token for a mesh, could reach `on support or floor` and nothing else: a dressing set that belongs on a
shelf or the floor had no rung at all, and the only way through was hand-editing the file, which is
what the cycle exists to make unnecessary. Every declared class now gets its own entry.

The pass also wrote the paperwork a killed pass left owed for E-049 (its fix was on `main` with no
report, no LOG line, and the backlog still saying `open`).

## Bugs fixed

### E-060: `mount_options` offered the two-way mount for the first surface class only

Must-fix: blocks **n**, common **n** (only a project with 2+ surface classes, and only a piece that
needs a non-first class), no workaround **y** (hand-edit the file) — 1 of 3, so not a must-fix. Taken
as the pass's one enhancement because the user-visible effect is an unreachable mount.

Root cause: `descriptor.rs`'s `surfaces.first()` insert. The comment's argument was list length
("one `or the floor` entry per class would put the list's length at the vocabulary's twice"), which is
true and was the wrong trade: an entry that does not exist cannot be reached at any price, and three
more rungs on a `M` cycle is a tap or two.

Regression check: `crates/bevy_emerge_core/tests/every_surface_class_has_a_two_way_mount.rs`
- `every_surface_class_has_a_two_way_mount` — **failed before** in a worktree at `0ffbd13`:
  *"every class the project declares must be offerable as `on <class> or floor` … Offered list:
  ["on floor", "on support", "on worktop", "on shelf", "on support or floor", …]"* — one two-way rung
  where three classes exist.
- `the_two_way_rungs_come_after_the_classes_they_lift_from` — the ordering the cycle reads as.
- `no_classes_means_no_two_way_mount` — the entry is derived from the vocabulary, never invented.
- `a_one_class_project_is_unchanged` — the common case does not pay for the fix.

The three ordering/count tests passed at the base too; that is deliberate — they are boundaries, and
the first test is the one that names the defect.

## Review

Reviewer **ran** (`reviewer` subagent over `f0b2145`, 59 s). Its verdict: *no defect that should
block the change; no consumer of `mount_options` breaks.* Four findings, and **one was a real defect
in my own arithmetic**:

- **P3, taken.** Both my comments said the list gains *three* rungs (13 → 16). The base list is 15
  (1 `OnFloor` + 3 plain + 1 two-way + 3 face + wall/ceiling/tiled + 3 decal + `InOpening`), and it
  becomes 17 — **two** more, not three. Both comments corrected to 15 → 17; the reviewer's
  arithmetic, re-derived by hand before the edit.
- It also confirmed, with line cites, the things I had only argued: `step_mount`'s `had` is `None` for
  an `OnSurfaceOrFloor`, so the lookup falls through to plain equality and each rung is distinct
  (`tiles.rs:5479`); this **fixes** a latent reset, because a hand-authored `OnSurfaceOrFloor { shelf }`
  was absent from the list and `map_or(0, ..)` sent it to `OnFloor` on one press of `M`;
  `valid_mount` already accepted any declared class (`vlm.rs:893-911`) and de-duplicates the classes in
  its refusal text; the longest new label, `on worktop or floor`, is 19 of 24 permitted characters.
- Prompt growth is N−1 lines of ~300 chars (~0.7 kB for the shipped vocabulary) on the *input*;
  `max_tokens` bounds output. Accepted.

Self-review, mine:


1. **Does the change do what the commit says?** Yes — the failing-before output names exactly one
   two-way rung with three classes declared.
2. **What could it break that no test covers?** The `M` cycle's wrap: `(i + 1) % options.len()` still
   terminates because the list is non-empty in every arm (`OnFloor` is always first). Duplicate
   *labels* are now possible in principle — `on worktop or floor` twice would need two `worktop`
   tokens, which `Vocabulary` refuses as a duplicate.
3. **Does the height carry survive?** `with_mount_height` returns `None` for `OnSurfaceOrFloor`, so the
   carry is a no-op on the new rungs exactly as it was on the one old rung.
4. **Is the ordering argument real or cosmetic?** Real for the author: interleaving two-way entries
   beside their plain class would make `M` alternate meaning twice per class.
5. **Does the fix weaken a check?** No test file was edited. One new test file added.
