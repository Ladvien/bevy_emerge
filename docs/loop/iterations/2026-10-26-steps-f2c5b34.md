# 2026-10-26 steps: the agent's steps are on screen, one row each (E-068)

Focus: present — the person watches what the agent did · Commits: `f2c5b34` · Outcome: shipped

## Summary

The brief's Collaboration direction, in Mixar's words: *"the agent shows what it is doing as steps
narrated by measured effect (the oplog's `result` lines, never raw logs), hangs captures on the step
that made them"*. Both halves existed and neither was on a surface a person watches — the receipt is
one row and the journal held refusals only, so an agent's eight-operation turn was eight toasts that
each replaced the last.

`steps::from_oplog` turns the log into rows, and the journal draws them.

## Enhancement: the steps panel

**User-facing goal:** a person can see, in one column, every operation the agent performed this session,
in order, each in the operation's own words, with a capture marked on the step that made it.

**Plan:** a pure `from_oplog` over the existing `ops::Entry` list, plus a drawn section in the journal.
**Files:** `crates/bevy_emerge_mapper/src/steps.rs` (new), `src/chrome.rs` (`Journal::steps`),
`src/notice.rs` (`record_steps`, the painted section), `tests/an_agents_steps_are_on_screen.rs` (new,
6), `tests/the_journal_draws_the_agents_steps.rs` (new, the surface).

**MCP:** no tool changed. This is a person's surface; the agent already had the log through
`emerge_read_oplog`.

**Four decisions worth stating:**

- **Every row's text is `Entry::result` verbatim.** That is the whole beat: the sentence an operation
  writes about itself is the sentence the person reads, so a step cannot claim more than the log says.
  A row that re-worded the result would be a second narrator, and two narrators disagree the first time
  one is edited.
- **A refusal is not a step.** A refused line carries no `result` — a refusal is what the editor would
  *not* do, and a row for it would tell the person the agent did something it did not. Refusals reach
  the person through the journal's own list, which is why both are in one column.
- **A capture hangs on its step and is not a row.** It names the log sequence it was taken at; one
  naming a sequence the log does not hold hangs on nothing rather than attaching to the nearest row.
- **The section is labelled**, because the steps read downward (the order they happened) and the
  refusals read upward (newest first, because a toast just showed the head). Two directions in one
  column need a word.

**Candidates considered and not chosen:** E-069 (the agent's plan on screen) and E-070 (auto mode).
Both are the next beats in the same catalogue and neither is a one-iteration change beside this.

## Borrowed from Mixar

The *Steps narrated by measured effect* row, now `shipped (E-068)`, naming `steps::from_oplog`.

**Trigger:** any operation an agent dispatches — the row appears when the operation log grows.

**Person sees:** `Cmd+E` opens the journal; the top of the column is `STEPS (n this session)`, one
indented line per operation, in order, and a `▪` on a row that made a capture.

**Agent gets:** nothing new. It already reads the same log through `emerge_read_oplog`, and this
surface deliberately adds no second channel.

**State:** none. The panel is a read of `oplog.jsonl`; nothing is written, and closing the panel loses
nothing because the log is the copy that matters.

**Refuses:** a line that is not a log entry. `from_oplog` shows the rows it can read and
`unreadable_lines` counts the rest, which the panel prints — a feed shorter than the file reads as a
complete session otherwise.

**Differs:** Mixar infers a step's *kind* from the tool name and re-labels a row by the counts its
script produced. bevy_emerge does neither: the operation already writes one measured sentence about
itself, so there is nothing to infer, and inferring would be the second narrator this beat exists to
avoid.

**Source:** `mixar@39b9d27:core/steps_format.py`.
