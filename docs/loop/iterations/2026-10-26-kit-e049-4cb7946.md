## Summary

A kind/effects chip click sent its label change through `editor::set_label`, which dispatches
`label_set`; `label_set`'s commit is `commit_measured`, the one door to `library.ron`. The caller then
ran `persist(project, Persist::Library, ..)`, whose arm calls `write_library`, serializing the same
`measured` a second time. Two `to_ron` → `save_atomic` round trips per click, plus two file-stamp
changes for the watcher to dismiss. The bytes on disk were right either way, which is why no test and
no diff could see it.

The pass that fixed it was killed before writing this report, its LOG line and its backlog update.
Nothing was left dirty; the fix itself is committed and green. This pass wrote the paperwork.

## Bugs fixed

### E-049: a chip click wrote `library.ron` twice

Must-fix: blocks **n**, common **y** (every label chip click on every library piece), no workaround
**n** — 2 of 3. Shipped previously as the pass's one enhancement; recorded here as the bug it is.

Root cause: `tiles::toggle_tag`'s success arm called `persist(project, where_to, said)` after
`editor::set_label` had already written the library through `commit_measured`.

Regression check: `crates/bevy_emerge_mapper/tests/a_chip_click_writes_the_library_once.rs`
- `a_chip_click_writes_the_library_once` — **failed before** with
  *"a chip click on a library piece must write `library.ron` once, got 2"* (assert left 2, right 1).
- `a_refused_chip_click_writes_nothing` — pins the other side: a token outside the vocabulary is
  refused before the file is touched, so the single write above is the edit's and not the door's.

The measure is a count, not the bytes: `tiles::library_writes_for_test()` reads a thread-local
incremented exactly where `commit_measured` writes, so libtest gives each test its own tally and a
file comparison cannot pass for the wrong reason.

## Review

Reviewer **could not run** (not spawned this pass). Self-review, mine:

1. **Does the change do what the commit says?** Yes — the count goes 2 → 1 and the one write carries
   the clicked token, so it is not "one write of the unchanged library".
2. **What could it break that no test covers?** The status line. `persist` returned the string
   `state.status.say` printed; the branch now says the `said` it already had. A chip click therefore
   reports the same words it reported before, which the first test does not assert — the wording is
   the labeler's, unchanged by this commit.
3. **Is the other `Persist::Library` caller in this file still correct?** Yes — every other library
   mutator in `tiles.rs` writes by hand and *needs* `persist`. Only this one went through an
   operation whose commit already writes.
4. **Is the thread-local a test hook that could lie?** It increments inside `commit_measured` at the
   same point the write happens, so a path that writes without passing there would read 0 — which the
   refusal test pins as the correct answer for a refused write.
5. **Does the fix weaken a check?** No test file was edited; one new test file added.
