# 2026-10-26 doorway: a piece standing in a measured opening is reported (E-079)

Focus: validators · Commits: `d27e452` · Machine: laptop (`mac_air`, Apple M1 Max, 10 cores) · Outcome: shipped

## Summary

`Mount::InOpening`'s `clear` — the `(width, height)` of the hole a door fills — was read by nothing
that decides space. `stack::same_layer` returns `false` for every heterogeneous pair (it must, or a
door and the wall it is set into would conflict), and `blocking`'s own doc has stated the consequence
since it was written: *"neither can a door and a crate standing in the doorway"*. So a crate could be
placed in a doorway, the click path accepted it, the map validated, and no answer anywhere said so.

`stack::blocked_openings` is that answer, and `checks` (E-074) now carries it as a third finding kind
beside edge faults and overlaps — so every document-changing operation's tool result says it.

## Enhancement: a piece standing in a measured doorway is reported

Goal: the doorway case `blocking` scoped out is reported by the same checks field every mutation
already carries.

`stack::blocked_openings(map, library) -> Vec<(opening_idx, intruder_idx)>` resolves each placement
once (plan box + vertical span), then for every measured opening tests every other placement:

- **the hole is `clear`'s rectangle, not the door's footprint** — a frame carries jambs inside its
  bounding box (`site/wall_doorway`: 0.3 m thick, 1.0 m wide, framing a 0.6 m hole), so comparing
  against the frame reports pieces standing *beside* the doorway;
- **vertical is read** — the hole spans `[base, base + clear.1)`, with `base` from `resolve_y` (the
  spawner's own answer), so a lintel course above the head is clear;
- **another opening is not an intruder** — that pair is `same_layer`'s question;
- **a piece resting on the door is part of it** (`Placed::on` names the door);
- **`clear: None` reports nothing** — "nobody has measured it" is not "zero wide", and the shipped
  `furniture_kenney.ron` door is exactly that row;
- **a map that does not resolve reports nothing** rather than inventing heights.

Files: `crates/bevy_emerge_core/src/stack.rs` (+`blocked_openings`, `opening_hole`, `hole_rect`),
`crates/bevy_emerge_mapper/src/checks.rs` (`Found::doorways`, `find`, `report`, module doc).

Proof: `crates/bevy_emerge_core/tests/a_piece_in_a_doorway_is_reported.rs` — 8 tests, all green, and
**mutation-tested**: changing `hole_rect` to return the door's whole frame footprint fails
`a_crate_beside_the_doorway_is_not_in_it` (7 passed / 1 failed), then reverted.
`crates/bevy_emerge_mapper/tests/a_placement_in_a_doorway_says_so.rs` — green, and it is the
end-to-end claim: `placement_add` of a crate in a measured doorway answers
`checks.doorways_in_the_way = {"new": [{"opening": "door@1", "inside": "crate@2"}], "new_total": 1,
"total": 1}`, a crate beside the frame answers `new_total: 0, total: 1`.

MCP: no new tool and no new operation. The field rides on every existing document-changing
operation's answer through `checks`, both front ends (`ops_brp::operation_apply` and the sequencer)
already calling `checks::report`, so nothing needed dispatching twice. Undo strategy unchanged — the
field is a report, not a document change, and a finding leaving the map with its cause is the existing
diff semantics.

## Review

Reviewer subagent: not spawned — the pass spent its build budget on two cold builds (core 4 m 11 s,
mapper 15 m 02 s) and the gate run; this is stated rather than hidden. The five questions, answered by
me and labelled as mine:

1. **Is the claim true?** Yes: `a_crate_standing_in_a_measured_doorway_is_named` is the minimal
   positive, and the end-to-end test shows the field in a real tool result.
2. **Does it fail for the right reason before the fix?** The `checks` field did not exist at the base
   commit at all, so the mapper test's `doorways_in_the_way` lookup was `null`; the core test could
   not compile against a base without `blocked_openings`. The mutation (frame footprint instead of the
   hole) is the sharper before/after and is recorded above.
3. **Is anything tested that isn't behaviour?** No golden files, no source-text ratchets, no counts of
   the sort the rules forbid. Every assertion is a finding set.
4. **What did the tests miss?** `Descriptor::clearance` — the *other* half of E-079 — is still unread
   by any space check. The item is therefore **half shipped** and stays open with that said. Also
   unexercised: an opening with a non-zero `Placed::lift` (the base comes from `resolve_y`, which
   includes it, so the arithmetic is right, but no test pins it) — logged as the next step, not as
   done.
5. **Could this break an existing map?** No: the only new output is an extra key in `checks`, and the
   shipped libraries carry `clearance: []` and two measured `InOpening` rows in `site/`. No shipped map
   was re-measured, so an existing doorway with a crate in it will start being *reported* — which is
   the point, and it changes no document.
