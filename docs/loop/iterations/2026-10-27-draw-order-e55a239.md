# 2026-10-27 core: the draw order compares only pieces that can overlap (E-020)

Focus: core draw order · Commits: `709d733..e55a239` · Machine: laptop (`Cs-MacBook-Pro.local`) ·
Outcome: shipped

## Summary

`draw_levels` levelled every piece against every piece ordered below it — `O(n²)` separating-axis
tests per call. `relevel_placements` runs on every change to the open map, `redraw_placements` after
every lift/tip/turn, and every spawn path reads `drawn_paints`, so a full-map edit on the shipped
town paid for about 0.5 M pair tests, nearly all of them between footprints metres apart.

The order now files each piece under the grid cells its bounding box covers (cell side = the mean
footprint span) and tests it only against pieces filed under those cells, plus the pieces too large to
file. Sharing a cell is necessary for two footprints to overlap, so the pruning cannot drop a pair
that matters; the levels are unchanged and the pairwise order is kept in the test as an independent
reference. Measured: **104** overlap tests instead of **81,003** on a 403-piece scattered town.

This pass also carried the previous pass's unpushed `709d733` to `main` (`c6285f1..e55a239`), and
committed the `backlog.json` evidence edit that pass left dirty.

## Enhancement: the same change

Goal: a map change costs work proportional to the pieces that can touch each other, not to the square
of the map. Files: `crates/bevy_emerge_core/src/draw_order.rs` (+~80), the new test file (+230).
No new operation, no undo, no preview change.

Equivalence is asserted four ways: against a copy of the pairwise order kept in the test, on a nested
chain (levels 0..3), on edge contact (shared cell, still disjoint), on a crossing (grid admits the
candidate, the SAT test orders it), and on a piece too large to file (kept aside and compared with
everything, or the pieces on a 400 m field would draw at level 0). `LEVEL_LIFT` is pinned so a speed
fix cannot quietly move every map's z-fight.

## Review

Reviewer could not run this pass (not spawned — the pass spent its remaining time on the compile
gate). The five questions below are mine.

1. **Does the change do what the commit says?** Yes — the base-failing output is a count
   (`81003` vs `81003`) and the fixed run prints `104`.
2. **What could it break that no test covers?** The one real risk is a piece whose bounding box is
   filed in a cell its footprint does not reach: that only *adds* candidates, never removes them, so
   it costs work and cannot change an answer. The reverse — a footprint reaching ground its box does
   not cover — is impossible for a rectangle.
3. **Is the cell size safe?** It is the mean span, so a map of one huge piece falls to the
   `MAX_CELLS_PER_PIECE` path and one piece is compared with everything; that path is tested (`an_
   enormous_piece_still_orders_against_what_it_covers`). A degenerate map (all spans zero) falls back
   to 1 m rather than dividing by zero.
4. **Does a non-finite corner change the answer?** No: `cell_range` returns `None` and the piece is
   kept aside, which is the "compared with everything" path the old code took.
5. **Does the fix weaken a check?** No test file was edited. One new test file added. The counter is
   a thread-local, like `library_writes_for_test`, so libtest's per-test threads cannot read each
   other's counts.
