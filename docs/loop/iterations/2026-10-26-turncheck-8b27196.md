# 2026-10-26 turncheck: an agent's turn is one undo step (E-071)

Focus: describe → set up → inspect → **present** (undoing an agent's turn) · Commits: `8b27196` · Outcome: shipped

## Summary

The brief asks for this by name: *"An agent's multi-step action is grouped into one undo step, so a
single undo reverts the whole agent step."* It was not true. Every dispatched operation became its own
`Undo::Logged`, so a three-operation turn took three Cmd+Z presses and the person pressing the key had
no way to know where the turn ended.

`emerge_present` already takes `operation_ids` — *"the operations this covers"* — so the agent was
already declaring the turn. `EditorState::group_turn` now folds that list into one `Undo::Group` at
presentation, which makes Cmd+Z and the presentation's `Undo all` take back the **same amount** rather
than being two answers to one question.

## Enhancement: a turn is one undo step

**User-facing goal:** after an agent presents a result, one Cmd+Z takes the whole turn back.

**Plan:** fold the presentation's `operation_ids` into one `Undo::Group` — the mechanism `generate`
already uses — and report how many were grouped.
**Files:** `crates/bevy_emerge_mapper/src/editor.rs` (`group_turn`, and a `Group` child order fix),
`src/ops_brp.rs` (`emerge/present` takes `EditorState` and groups; the answer carries `grouped`),
`tests/an_agents_turn_is_one_undo_step.rs` (new), `docs/loop/borrowing-from-mixar.md` (the catalogue
row), and the `Undo::Logged` refusal arm inside a group.

**MCP:** `emerge/present` gains `grouped` in its answer — how many of the turn's entries became one
(`0` when it presented one operation, or ids the stack no longer holds). Nothing else changes shape.
Preview and undo strategy are untouched: a presentation changes no document, and the grouping is on
the editor's stack, not in the log.

**Candidates considered and not chosen:**

- *E-084*, now filed: `emerge_undo_operation` with no id walks the operation **log**, so an agent's
  newest-change undo takes back one operation where Cmd+Z takes the turn. Found live *after* the fix
  worked, and it is the same "two front ends disagree" class — but it lives in the BRP undo handler,
  not in the grouping, and fixing it means deciding whether the agent's undo should follow the
  person's stack. Its own iteration.
- *E-066*, `map_remove`: `map_create` declares `Undo::None` because the faithful inverse of a create is
  a removal no operation carries.
- *E-082*, `rules_set`'s missing library check: needs a decision about where a library comes from on
  the server, not a small fix.

## Borrowed from Mixar

The catalogue row *Turn checkpoints* — `mixar@39b9d27:core/turn_checkpoints.py`,
`mixar@39b9d27:core/checkpoint_timeline.py`, `mixar@39b9d27:ui/operators/checkpoint_ops.py` — is now
`shipped (E-071)`, naming `EditorState::group_turn`.

**Trigger:** an agent presents a result — `emerge/present`, the same call that puts the Keep/Undo all
question on screen.

**Person sees:** the confirmation card as before. What changes is the keyboard: ONE Cmd+Z now takes
back everything the presented turn did. The INSPECTOR's UNDO row reads "3 changes" instead of naming
one placement.

**Agent gets:** `grouped` in `emerge/present`'s answer — how many of the turn's entries became one. So
it can say "one undo takes this back" only when that is true.

**State:** the turn's leaves on the editor's undo stack are folded into one `Undo::Group`, in the
order the operation log can answer (newest first). Nothing is written to the map or the log; undo and
redo both walk the group, and the group is closed under inversion like every other entry.

**Refuses:** nothing new. A presentation naming an id that is not in the log was already refused, and
still is. A presentation naming no operations groups nothing, so a turn that changed nothing cannot
swallow the person's next edit.

**Differs:** Mixar snapshots the whole document to a file before each turn and restores it;
bevy_emerge has no whole-document snapshot and does not gain one. It groups the turn's own logged
leaves instead — smaller, no disk budget, and one source of truth (the oplog) rather than two.
Mixar's position is "the number of user messages"; here the boundary is the presentation's
`operation_ids`, which the agent already declares.

**Source:** the two files above, read at the pin.

## Live proof on the real project

Three `placement_add` operations on Sanctuary's `town` through the running editor, then a
presentation:

```
ids: 3
placements before: 730
present: {"grouped": 3, "presentation": "present-1", "steps": 3}
```

`grouped: 3` is the declaration that the turn is one entry, and its phrase on the INSPECTOR reads
`3 changes` (`placed crate@1 …, +2 …`) rather than naming one placement.

**And the live run found a gap the tests did not:** one `emerge_undo_operation` (the *agent's* undo,
not Cmd+Z) took the map 730 → **729**, one placement, where Cmd+Z leaves 727. That is **E-084**: the
agent's undo handler walks the operation log and never reads the grouped stack. Filed rather than
fixed, because it is a different front end and the fix is a decision about which history an agent's
undo should follow.

## Review

**The reviewer could not run, for the third iteration running.** The `reviewer` subagent was spawned
and died on the same cloud limit (`HTTP 429 … You reached your Pro 5-hour limit`); it takes no model
override and the account is capped for the window. So the review below is mine.

What it turned up, in the order I would have set it:

| Question | Finding |
|---|---|
| **1. Does one Cmd+Z really take the whole turn?** | It did not, and the failing-first test said so before any fix: three operations, one Cmd+Z, **two crates left**. That is the bug reproduced exactly. |
| **2. Why did the group say "3 changes" and undo one?** | **The real defect.** Children are undone in order; the stack is oldest-first; `ops::undo` refuses a change while a newer one in the same scope is in effect. So the three were applied in authoring order, the first two refused, and `Group`'s `Refused => {}` dropped them silently. Fixed by reversing the children at grouping time — and the refusal inside a group now reaches `Status::problem` instead of vanishing. **A count printed (`ops.len()=3` then `1`) is what located it**; reading the code did not. |
| **3. Does the group swallow a person's earlier edit?** | No, and `a_turn_does_not_swallow_a_persons_earlier_edit` pins it: only `Logged` entries whose line the presentation names are taken, and the person's own entry is still on the stack afterwards (`undo_depth == 1`). |
| **4. Can an empty presentation group anything?** | No — `group_turn` returns 0 for fewer than two ids, so a turn that changed nothing cannot collapse the person's next edit. Pinned by `a_presentation_with_no_operations_groups_nothing`. |
| **5. Is `grouped` honest?** | Yes, and deliberately so: it reports what *happened*, not what was asked. The live run is the evidence — `grouped: 3` while the agent's own undo still took one, because the grouping is real and a different front end ignores it. |
