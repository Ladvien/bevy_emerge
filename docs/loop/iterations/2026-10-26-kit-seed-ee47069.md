# 2026-10-26 kit: arriving on the Meshes shelf is a selection, so it goes through `piece_select` (E-050)

Focus: kit/parity · Commits: `5bb6dd7..ee47069` · Machine: big (`Cs-MacBook-Pro.local`, no Sanctuary checkout) · Outcome: shipped

## Summary

`right` and a click on the `MESHES` chip both point the Meshes shelf at a piece, and both wrote
`selected_library_id` by hand. The very next `down` dispatched `piece_select`, so the operation log
recorded the walk and not the arrival — an agent reading the log could not see the shelf had pointed
itself at anything until somebody pressed an arrow, and one question had two answers depending on
which key asked it.

Both seeds now dispatch the same `piece_select` a row click and an agent use. The Tiles tab keeps the
direct write on purpose, and a test pins that boundary.

## Bugs fixed

### E-050: the Meshes shelf's arrival was a hand write, not a selection

Must-fix: blocks **n**, common **y** (every keyboard arrival on the shelf), no workaround **n** — 2 of 3.
Shipped as the pass's one enhancement rather than a bug, because the user-visible effect is the log
and the parity table, not a wrong highlight.

Root cause: `tiles::move_selection`'s `FocusLibrary` arm and `on_shelf_click`'s `Shelf::Library` arm
each did `state.selected_library_id = Some(land)`. The filtered-out re-arm and the walk step in the
same function already called `editor::select_piece`, which dispatches `piece_select` and applies the
answer through `apply_selected`, so the log line and the `focused_pack` clear were already the
operation's job.

Regression check: `tests/the_library_seed_is_a_selection.rs`
- `the_library_focus_key_selects_through_the_operation` — **failed before** with
  *"arriving on the shelf is one selection, so it is one `piece_select` line: []"* (0 lines, wanted 1).
- `the_library_shelf_chip_selects_through_the_operation` — **failed before**, same message from the
  chip path.
- `the_tiles_tab_seed_is_not_logged_as_a_meshes_selection` — passes both ways; it is the boundary, not
  the fix. `piece_select` names the Meshes shelf, and on the Tiles tab the list is a tile's source,
  which no operation names yet. Logging it there would make the log claim a selection that did not
  happen.

Both failing tests read the log from `project_dir/oplog.jsonl` on disk, not editor memory — the file
an agent reads. The tests were re-run against the pre-fix source (the two blocks reverted, then
restored) to get the failing output quoted above.

## Review

Reviewer **could not run** (subagent not spawned this pass — the pass spent its build budget on three
full `bevy_emerge_mapper` compiles). Self-review, mine:

1. **Does the change do what the commit says?** Yes. Both seeds call `editor::select_piece`, which
   dispatches `piece_select` and applies the answer; the failing-before tests are the evidence.
2. **What could it break that no test covers?** The seed now runs a whole operation dispatch on a key
   press, so a *refusal* is possible where a field write was not — `piece_select` refuses an id the
   library does not hold, and `library_landing` only returns ids from `library_ids`, so the refusal
   is unreachable from this path. If it ever became reachable, the refusal goes to `status.problem`
   and the highlight stays where it was, which is the right failure.
3. **Does the seed now double-log a re-press?** No — the call is inside `if
   state.selected_library_id.is_none()`, so a second `right` with a selection already made is silent,
   as it was.
4. **Is the Tiles-tab half a real boundary or a dodge?** A boundary, and it is the one the walk step
   next door already draws (its comment says the same thing). A test pins it so a later migration
   cannot log a Meshes selection for a tile's source.
5. **Does the fix weaken a check?** No test file was edited. One new test file added; `UNMIGRATED_MAX`
   untouched (no action became migrated — `FocusLibrary` still names no operation, because it does
   two things: switch the list and seed it).
