## Bugs fixed
### #173: a second Shift-click on a piece while the note box is open is not picked
Must-fix: blocks yes (#89's "Shift-click more" and #95's clip), common yes (every note on more than one piece), no workaround yes (a person has no other route; only an agent's `note_add {"pieces": [...]}`).
Root cause: `drive_note` ran in the tuple gated by `not_typing`, and `Fields::typing` counts `note_box.draft`, so the box the first Shift-click opened switched `drive_note` off; its own `collecting` branch could never run. Fix: `Fields::typing` = `typing_beside_the_note_box() || note box`; `drive_note` runs behind the new `note_takes_clicks` (every field but the note box, and no filter box) and still decides which open box takes a click. Every other reader of `typing` (the key census, `not_typing`) is unchanged, so the box still holds the keys.
Regression check: `a_person_shift_clicks_two_pieces_into_one_note::two_shift_clicks_leave_one_note_on_both_pieces_and_not_the_third` (Shift+N, two Shift-clicks, a word, Enter, injected as a person) failed on main with `left: ["site/wall@0"] right: ["site/wall@0", "site/wall@2"]`; after, `cargo test -p bevy_emerge_mapper --test editor note`: 31 passed.
Live: on the scratch town, the frame after the second Shift-click reads `LAST note on 2 piece(s): Shift-click more, type it, Enter saves, Esc cancels` (capture `demo_notes_end_to_end_0/f048`), and `town.notes.ron`'s n2 targets `Placement("kitchen_cauldron")`, `Placement("kitchen_table")`.
