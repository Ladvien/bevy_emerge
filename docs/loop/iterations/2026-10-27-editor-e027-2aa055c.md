## Summary

E-027 has been open since 2026-10-22 and its own evidence names the missing piece: *"Gap: no test
shows a human turn writes one entry, not two."* Since 6aa6185 the turn keys dispatch the registered

undos**, and the second Cmd+Z would replay a turn the first had already taken back.

bites by putting the old second record back for one run.

No product change, so no enhancement and no accept difference is expected; `accept.py` was run for
the record.

## Bugs fixed

### E-027: a human R or T turn writes two undo records (oplog line and stack entry)

Must-fix: blocks **no**, common **no**, no-workaround **yes** — 1 of 3, so **not** a must-fix. The
defect was never observed in a live run; it is a design question about one undo history (E-013,
B-019), and 4364dd4 already answered it in the code.

Root cause (had it existed): `turn_under_cursor` recording both `state.record_logged(line, …)` and
`state.record(Undo::Turned { … })` for the same keypress, leaving the stack holding two entries
for one act.

Regression check: `crates/bevy_emerge_mapper/tests/a_persons_turn_is_one_undo_step.rs::a_persons_turn_writes_one_undo_entry_and_one_cmd_z_takes_it_back`

**Failed before, passes after — measured, not asserted.** With

```rust
state.record_logged(line, summary, false);
state.record(Undo::Turned { index, yaw: was_yaw });   // the pre-4364dd4 record
```

in `turn_under_cursor`, the test failed at the stack count:

```
R wrote 2 undo entries for one keypress. A second entry means the first Cmd+Z takes back one half
of the turn and leaves the other on the stack, so the next Cmd+Z undoes a change that has already
happened.
  left: 2
 right: 1
```

With the line removed (i.e. the code as `main` has it) it passes: one oplog line with
`source: Human` and `op: placement_set_yaw`, one stack entry, one Cmd+Z puts the yaw back on the
screen, in the map and in the file, and a second Cmd+Z changes nothing.

What the test drives, and why each step is the person's rather than the test's:

- The real `R` key through `ButtonInput<KeyCode>`, with the window's cursor set in `PreUpdate` after
  `InputSystems`, so `sense_pointer` reads the injected pointer — the pattern
  `a_person_removes_a_piece_and_undoes_it` uses.
- `Esc` first. The editor opens with a brush armed; `R` with a brush in hand steers the *ghost*, not
  the piece under the cursor (`drive_ghost`'s subject rule). A person turning a wall on the map
  presses `Esc` first, so the test presses it rather than writing `state.brush = None` past the key.
- One frame per press, then a frame with no keys held, so a held `R` cannot repeat into a second
  turn (`keys::REPEAT_SECS`).

quoted above, and the budget went on two cold rebuilds (11 m 14 s and 8 m 00 s on the same test

2. **Does it fail for the right reason?** Yes: the count assertion, not a build error and not the

   the receipt.
