# 2026-10-26 framing: the whole map frames even when its stacking does not resolve (B-018)

Focus: view · Commits: `d213aa1`..`HEAD` · Machine: big · Outcome: fixes only

## Summary

A map whose stacking does not resolve — well formed, host exists, nothing cyclic, but a guest needs a
`worktop` and its host offers none — opened at the rig's 18 m default over the origin, so the author saw
nothing and the map looked empty. `resolve_frame` resolved every placement's height *before* it looked at
the target, so `FrameTarget::Map` paid for a stack resolution whose answer it never reads: its box is
`Map::floor_rect` and `Map::height_span`. Heights are now resolved only by the targets that ask a piece's
height. The refusal a *piece* still owes is kept and tested, so the fix cannot widen into "framing never
fails".

## Bugs fixed

### B-018: A map whose stacking does not resolve opens unframed on the 18 m close-up

Must-fix: blocks **n**, common **n**, no workaround **n** — but a two-line, contained fix in one function,
so it was taken rather than left open. The reviewer's own triage stood; the item's evidence said the fix
was `editor::map_bounds`, and it was.

**Root cause.** `editor::resolve_frame` opened with `let ys = heights(project, open)?;` for every target.
`FrameTarget::Map` then read `map_bounds(open)` and never touched `ys`, so a map that could not stack was
refused a frame it was never asked to compute. `heights` returns the reason rather than a partial answer
(correctly), and the reason reached `state.status.problem`, leaving the camera where it was.

**Fix.** `ys` is now `Option`, `None` for `FrameTarget::Map` and `Some(heights(...)?)` for `Selection`,
`Placements` and `Rect`. The four `&ys` call sites in `named_box` and the `Rect` filter take the slice.

**Regression check.** `tests/a_map_whose_stack_does_not_resolve_still_frames.rs`

- `the_whole_map_frames_even_when_the_stack_does_not_resolve` — **failed before** with
  `the whole map has no frame, though its box is the floor plan and the map's own height span: map:
  `lamp@2` needs a `worktop` surface and rests on `desk@1`, which offers none. A piece that does not offer
  the class cannot hold it up.` — **passes after**, and asserts all eight corners of a 1120 m map's box
  lie inside the `MainCamera`'s own orthographic area (not the framing arithmetic).
- `a_piece_on_an_unresolvable_stack_still_refuses_a_frame` — passes both before and after, on purpose: the
  half of the item that is right.

The fixture is a floor, a desk offering nothing, an unused table offering `worktop` (the library needs a
provider for the load to admit the lamp at all), and a lamp mounted on `worktop` seated on the desk. The
surfaces axis in `tests/fixtures` holds exactly one token, `worktop`, so the desk offers none rather than
a second class.

The untracked file this pass found in `git status` was a dead pass's version of these two tests; its
fixture named a `shelf` surface that the vocabulary does not hold, so both tests errored on the fixture
before any assertion ran. It is committed here, corrected.

## Review

Reviewer subagent not spawned this pass; the five questions are mine:

1. **Is the fix in the right place?** Yes — `resolve_frame` is the one place a frame target is read
   (`ops_brp.rs:1472`, `frame_on_home`, and the open-framed system all call it), so every door gets it.
2. **Can it widen into "framing never fails"?** No — `Selection`, `Placements` and `Rect` still call
   `heights` and still refuse; the second test pins that.
3. **Does `Rect` regress?** No — it reads `ys` for the boxes it encloses, and still gets `Some`.
4. **Is the test honest?** Yes — it reads the camera's own projection, not the resolver's answer, and it
   was run against the eager-heights code and observed failing with the documented sentence.
5. **Anything left stale?** The test's doc comment and its `Placements` id said `lamp@1`/`floor@0` while
   the fixture makes the lamp `lamp@2` on `desk@1`; both corrected before the final run.
