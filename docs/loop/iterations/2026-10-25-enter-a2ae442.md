# 2026-10-25 enter: an agent's `map_open` on the menu enters the editor (E-078)

Focus: E-078 + B-050 · Commits: `26cf131`, `a2ae442`, `2b5b1b4` · Outcome: shipped

## Summary

The acceptance script reached 11/11 before this run, and one of those eleven was not measuring the
product: `open_map` passed because the script **relaunched the editor on the map** and recorded a
`workaround` in the step's row. In the product, an agent that made a map from the menu could not work
in it — `map_create` and `map_open` both applied, `emerge/state` reported the map, and the window
stayed on the MAPS column.

`map_open` applied on the menu now enters the editor on that map, through the same path the MAPS
column's Enter key takes. The relaunch is gone from `accept.py`, so the headline number measures the
editor again. `reached 11/11` is unchanged — what changed is that every one of the eleven is now the
product's own behaviour, and the JSON carries no `workaround` key at all.

## The gap, in one line

`EditorState` does not exist on the menu and `editor::apply_pending_door` runs
`in_state(Screen::Editor)`, so the door-request mechanism cannot cross an editor boundary. The menu
enters the editor through `Chooser::Chosen` → `screen::open_the_door` on `OnExit(Menu)`, and that is
the screen's path, not an operation's. An operation could load a map; it could not move a screen.

## The fix

`ops_brp::operation_apply` now takes `Option<Res<State<Screen>>>` and
`Option<ResMut<NextState<Screen>>>` and reads the **state**, not the presence of a resource —
`MenuOpening` is inserted at plugin build and is on every screen, and `EditorState`'s absence is a
fact about the editor rather than a name for the menu.

When the operation is `map_open`, it applied, and the screen is `Menu`, the operation puts the loaded
project and map into `Chosen` and sets `NextState(Editor)`. Those are the same two lines
`chooser::open_the_selection` runs for Enter on the MAPS column, which matters more than brevity:
`screen::open_the_door` installs the project and map through `Opened::insert_into`, an exclusive
system, so `OnEnter(Editor)` — the very next schedule — finds them. Inserting `Project` from the
operation instead would have put a loaded project on a screen with no door, and a `NextState` read a
pass late runs `OnEnter(Editor)` against a world with no project: the panic `open_the_door`'s own
note records. **There is one way into the editor, and this is it.**

Three smaller decisions, each an assertion in the new test:

- **Applied but not loaded is a refusal, not half an entry.** `map_open::commit` always sets both on
  the menu, so this is the shape of a defect rather than a use; the alternative is an editor entered
  with a project and no map, which is the one state it cannot be entered in.
- **The `door_request` branch is gated `&& !on_menu`.** From a door it is the old behaviour; from the
  menu the entry has already happened.
- **No receipt is carried across the entry.** `EditorState` starts fresh on `OnEnter(Editor)` and the
  person sees the map open; a new resource for it would be a second answer to "what just happened".

## `accept.py`

`step_open_map` applies `map_open`, then waits for the map on the **same** editor:

    self.editor.wait_ready(lambda s: ((s.get("map") or {}).get("name")) == MAP, limit=60)

and on a timeout records `map_open applied but the editor stayed on the menu`, so its dependents
skip — which is the honest measurement rather than a workaround. The relaunch, the second client and
the `workaround` field are gone; `run()`'s `finally` still reaps every editor in `Run.editors`, and
the two comments that claimed a relaunch no longer do. `test_accept.py` gained `TheOpenMapStep`,
which asserts a passing `open_map` row carries no `workaround` (12 tests, all green).
