# The bevy_emerge MCP tools

Generated from the server's own tool declarations. **Do not edit this file** — it is written by `cargo run -p bevy_emerge_mcp -- --emit-docs`, and a test fails when it does not match the server.

The server speaks the Model Context Protocol over **stdio**, and reaches the running editor over the Bevy Remote Protocol on `BEVY_BRP_PORT` (default 15702). It writes nothing to disk itself: the editor owns the project directory, and every file the editor writes is written by the editor.

## The tools

### `emerge_list_operations`

Every operation the running bevy_emerge editor knows, with each one's parameters' JSON schema and how it is undone. Call this before emerge_apply_operation so the parameters are the ones the operation actually takes. Returns the list; it does not change anything.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `emerge_preview_operation`

What an operation would change, and nothing changed: the map, the data file and the operation log are all left alone. Use this to check a proposal before applying it. Returns what would change, or the refusal.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

### `emerge_apply_operation`

Run one of the editor's operations. Changes the open map, writes the data file, and appends a line to the operation log. Set dry_run to true to see what would change without changing it. Returns the operation's id, which can be cited in a report to the developer, and the log's own record of it.

| annotation | value |
|---|---|
| `readOnlyHint` | false |
| `destructiveHint` | false |
| `idempotentHint` | false |

### `emerge_read_oplog`

The editor's operation log, newest last. Every operation appends one line, whether a person or an agent did it, and an undo is recorded as a new line rather than a deletion. Read it to see what has been done to this project.

| annotation | value |
|---|---|
| `readOnlyHint` | true |
| `destructiveHint` | false |
| `idempotentHint` | true |

## How the two paths converge

Every operation writes the data file, and the editor watches that file. So:

- an **agent** calls `emerge_apply_operation`, the editor writes the file, and the editor's own state is already the new one;
- a **person** edits the file in a text editor, the watcher notices within a quarter of a second, and the editor re-reads it — **and keeps what it had if the file does not parse**;
- a **person at the keyboard** uses the editor's own controls, which dispatch the same operations.

The measured latency of both paths is in the iteration report.
